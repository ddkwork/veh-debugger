# VEH Debugger v1.2.1

This release adds authenticated remote backend connections, broader external-backend
inspection, and smaller MCP analysis responses. It also fixes remote session
recovery, breakpoint removal races, and missing or misleading trace results.

## Upgrade notes

- Local debugging still uses the VEH DLL when no backend is selected. External
  backends are optional and are not included in this release; their negotiated
  capabilities determine which operations are available.
- The VSIX and binary ZIP now include `veh-remote-runner.exe` alongside the adapter,
  MCP server and x64/x86 payload DLLs. Remote connections require a configured
  runner, pinned TLS certificate and private token file. Update both the frontend
  and runner for the new startup diagnostics; a backend must also implement the
  optional startup-report helper to supply a structured failure reason.
- Guest attachment and VM-wide inspection are separate from host-process debugging.
  Guest process discovery and guest launch/stopOnEntry remain unsupported.
  Unsupported guest launch is rejected before creating a host process or replacing
  the current session. VM-wide control requires an explicitly supporting backend.
- Existing `veh_trace_memory` calls retain first-write behavior. Supplying
  `duration_ms` selects timed collection. Existing caller-trace second-based
  arguments and results remain available alongside millisecond precision.

## Added

- **Authenticated TCP backend connections (MCP).** A resident runner starts the
  backend agent, owns remote work and host-process launches, and supports bounded
  reconnection without treating a remote PID as a local PID. Driver-based analysis
  VMs and VirtualBox/WHPX analysis hosts use the same frontend transport; the latter
  runs the runner on the analysis host, not inside its inner guest. Connections use
  pinned TLS and one fresh challenge/proof authentication exchange. Tokens are not
  sent with commands or included in diagnostic output.
- **External backend attachment and launch.** Registered backends or explicit agents
  can serve host processes through the existing IPC commands without DLL injection.
  Guest attachment validates the backend's PID and address width without opening
  the same numeric host PID. `target_scope="vm"` permits a VM-only session without
  a process PID or a host process monitor.
- **System inspection through supporting backends.** New interfaces cover
  physical/kernel memory, address translation, MSR/CPUID, I/O ports, IDT/APIC, PCI,
  kernel modules, address-space selection and debugger-time compensation. Supporting
  backends can also expose machine events, hidden hooks, LBR and Intel PT records.
  These interfaces do not add those facilities to the VEH DLL.
- **VM control and vCPU instruction trace.** `veh_virtual_machine` exposes explicit
  whole-VM status/pause/resume and a bounded paused-vCPU interpreter batch.
  CR3/CPL/RIP boundaries stop before execution, and partial failures retain completion
  and loss metadata. This is independent of process thread stops and is deliberately
  excluded from process-scoped batch/capture steps and breakpoint actions.
- **Kernel debugging over GDB RSP.** Machine-wide pipe/COM/TCP/UDP connections support
  CPU registers, memory, stepping, breakpoints and watchpoints with a compatible
  remote stub. These operations can halt the whole target machine.
- **Timed memory-access collection.** `veh_trace_memory.duration_ms` collects access
  sites with hit counts, first-thread registers and explicit `dropped_hits`.
  The VEH backend supports write or combined read/write collection, identifies
  locations as `addressIs="next_instruction"`, and reports registers after the first
  access. It does not support read-only collection or per-hit read/write classification.
- **Bounded MCP batches.** With no attached session, the first top-level
  `veh_batch` step may launch or attach, then run analysis in the same request.
  Lifecycle operations remain rejected in repeated/nested steps and breakpoint
  actions. Per-step `result_fields` selects returned fields while later references
  and conditions retain the complete original results.
- **Response budgets and schema manifests.** `max_output_bytes` moves an oversized,
  field-selected batch report to a new MCP-host JSON file and returns its path,
  size, SHA-256 and explicit partial metadata. Callers own retention and cleanup.
  `veh_toolbox manifest` fetches up to 64 workflow schemas together and returns a
  short unchanged response when its reusable handle still matches.

## Changed

- MCP input, heartbeat and kernel-debug pipe waits are event-driven instead of
  periodically polling.
- Backend descriptions, CLI help and Korean/English setup documentation distinguish
  native host debugging, guest attachment and VM-only sessions, including their
  unsupported operations.

## Fixed

- **Remote detach and reattach recovery.** Missing or late detach replies retire the
  old work instead of allowing it to be reused. Dead agents and closing jobs are
  excluded from reattachment, and exact process-handle notifications cancel dead
  connections. Reattaching the same backend/scope/PID waits for the old remote
  connection to close; detached host targets survive backend death.
- **Authentication and long commands.** Successful authentications no longer consume
  the failed-attempt quota. Pending proofs reserve failure slots without erasing
  earlier failures. In-flight commands and response delivery keep the TCP connection
  alive through idle input intervals.
- **Ambiguous remote launches.** Explicit rejection or failure before request
  delivery clears retry state. An uncertain or lost reply retains the same launch
  identity so a retry does not create a second process.
- **Startup and query diagnostics.** Failed remote work opens preserve the startup
  stage, actual agent exit code and available OS errors before cleanup. Structured
  startup records add validated common error/detail identifiers without interpreting
  backend-specific exit numbers or forwarding logs. Query and trace failures no
  longer appear as successful empty results, guessed missing stops/hooks, or an
  assumed remote target crash. Pipe connection timeouts retain their last OS error.
- **Lifecycle response loss.** VEH Detach/Shutdown replies remain available until the
  client closes, with a bounded drain instead of an immediate disconnect that could
  discard the response or an unbounded flush.
- **Breakpoint removal races.** An in-flight debugger INT3 dispatched after removal
  replays the restored instruction instead of skipping its first byte. This prevents
  instruction corruption and target crashes during repeated caller traces.
- **Continue and step results.** Continue discards stale stop events for resumed
  threads and checks stopped state when supported. Backend step refusals report
  immediately instead of waiting for a stop timeout. Unsupported pause/terminate
  no longer reports success, and rejected termination preserves the session.
- **Caller traces.** Hypervisor caller traces no longer automatically continue then
  pause the target, which could leave every thread suspended after collection.
  The VEH INT3 backend retains its resume/pause behavior. A no-hit window returns
  `totalHits: 0`; both `durationMs` and legacy `durationSec` are returned, preserving
  subsecond precision. Millisecond input takes precedence if both units are supplied.
- **Breakpoint capacity errors.** Explicit resource exhaustion is distinguished from
  other failures instead of assuming that every backend has four hardware slots.
  Numeric backend capacities are still not negotiated.
- **Long shellcode execution.** The IPC wait includes the requested execution timeout
  plus setup/cleanup time instead of failing at the default three-second deadline.
- **Compare-exchange trace writes.** Basic-block traces record `cmpxchg`,
  `cmpxchg8b` and `cmpxchg16b` writes, with or without `LOCK`, in inline events,
  file streams and aggregate tables. Actual before/after bytes are retained even
  for failed comparisons and same-value writes.
- **Conditional dependencies and memory accesses.** Conditional register reads/writes
  retain the previous destination origins conservatively. Memory-source `cmov`
  reads are collected on either outcome. Conditional or masked accesses whose
  executed bytes cannot be determined are explicitly unsupported, and dependency
  results are marked incomplete instead of silently dropping or inventing accesses.
